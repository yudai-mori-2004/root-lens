# 24. Consent evidence chain

## 目的

撮影前の現場合意とスタッフ個人の同意、撮影後の現場監督者による承認、実際に承認された撮影データを、一つの来歴として追跡できるようにする。署名済みPDFの原本はGoogle共有ドライブ「RootLens Submit」に保存し、WebのDBは原本の所在とSHA-256を記録する。

販売先へ渡す`rootlens-evidence.json`は、使用した同意記録、現場監督者の承認、その時点で承認されたファイル一式を結ぶ索引である。RootLensの署名鍵や第三者証明書は使わない。同意PDFの原本確認は、証跡一式に同梱したPDFとJSONに記録したSHA-256の照合によって行う。DriveのファイルIDやURLは外部向けJSONへ含めず、RootLens内部の原本管理にだけ使う。

## 当事者が行うこと

### 事業所の登録者

SMS認証でログインし、事業所情報を入力して現場合意書へ同意する。同意が完了すると事業所が作成され、登録者は最初の現場監督者になる。RootLensによる事前審査や利用開始状態の切替は設けない。

### スタッフ

管理者からLINE等で受け取った個別の招待リンクを開き、SMS認証後に撮影参加に関する同意書へ同意する。手書きの署名画像や専用アプリは必要としない。

### 管理者・現場監督者

スタッフの追加と招待、撮影データの確認、承認、アップロードを行う。DesktopはブラウザでのSMSログインからRootLensセッションを取得し、その人が操作できる事業所をAPIから取得する。事業所認証ファイルは使わない。

## 識別子

| 識別子 | 意味 |
| --- | --- |
| `site_id` | 撮影場所・事業所 |
| `person_id` | 一つの事業所に所属する人 |
| `identity_id` | SMS認証済みの利用者 |
| `agreement_record_id` | 一回の現場合意またはスタッフ同意 |
| `unit_id` | 一つの撮影単位 |
| `approval_event_id` | 一つの撮影単位に対する提供前承認 |
| `evidence_id` | 納品時の証跡索引 |

同姓同名は`person_id`で区別する。電話番号そのものは納品物へ含めず、署名PDFには末尾4桁だけを表示する。

## 同意原本

### 原本の構成

同意ごとに新しい`agreement_record_id`とPDFを作る。既存のPDFは上書きしない。PDFには、同意時点の全文と次の同意記録を収める。

- 署名者の氏名
- 事業所名
- SMS認証を使用したこと
- 認証した電話番号の末尾4桁
- サーバーが確定した同意日時
- 書式版
- `agreement_record_id`

署名操作の証拠は、SMS認証済みの`identity_id`、同意操作、確定本文、サーバー時刻を結び付けたDB記録である。手書き風の画像は付けない。

### DriveとDBの役割

```text
RootLens Submit/
  現場データ収集/
    <事業所名>/
      現場合意書/
        site-agreement__<agreement_record_id>.pdf
      スタッフ同意書/
        staff-consent__<agreement_record_id>.pdf
      承認済みデータ/
        <unit_id>/
          ...撮影データ
```

Driveファイルには`agreement_record_id`、`site_id`、文書種別、文書版を`appProperties`として付ける。DBには次を保存する。

- `agreement_record_id`
- `site_id`と、スタッフ同意の場合は`person_id`
- SMS認証済みの`identity_id`
- PDFへ表示した署名者名と電話番号の末尾4桁
- 文書版とテンプレートのSHA-256
- 同意文言と同意日時
- DriveファイルID
- 保存後にDriveから確認したPDFのSHA-256
- Driveへの保存完了日時

Driveの版履歴には依存しない。改定または再同意では新しいPDFを作り、以前のPDFを残す。撤回も原本を変更せず、別のイベントとして記録する。

### Driveとの同期

登録・招待同意の開始時に`agreement_record_id`とDriveファイルIDを一度だけ割り当てる。事業所登録では画面が保持する登録操作IDを使い、招待では招待IDを使う。同じ操作を再送した場合は同じID、同じ同意日時、同じ署名者情報からPDFを再生成する。既に同じPDFが保存されていれば新しいファイルを作らない。

保存処理は次の順で行う。

1. SMS認証と、HTTPリクエスト内の`agreed: true`を確認する。画面のチェック状態だけでは記録しない。
2. DBで登録操作または招待を排他的に確保し、同意日時、署名者情報、文書版、DriveファイルIDを固定する。
3. その情報からPDFを生成し、Driveへ保存する。既存ファイルがあれば内容、保存先、`appProperties`、SHA-256を照合する。
4. DBトランザクションで原本のSHA-256、同意記録、所属、招待の使用済み状態をまとめて確定する。事業所登録では事業所と最初の現場監督者もここで確定する。

通信が途中で失敗した場合は同じ操作IDで再試行する。DriveだけにPDFがあってもDBで確定するまでは同意・所属の成立とみなさない。再試行時に原本を照合してDBの確定へ進む。未完了の操作はDBに残し、原本を別の同意として再発行しない。現在は未完了ファイルの自動削除を行わない。再試行されずに残った操作は、DriveとDBの両方を確認してから管理者が回収する。

スタッフの削除はDB上の所属を解除し、有効な同意を今後の承認には使えない状態にする。招待リンクも失効させる。成立済みの同意PDFはDriveから削除しない。過去の撮影単位の証跡から、その時点でどの書面に同意していたかを確認できるよう残すためである。スタッフのSMSアカウントへDrive権限を直接付与する仕組みはないため、Drive側で個人のアクセス権を解除する操作は発生しない。

## 事業所とスタッフの通常フロー

### 事業所登録

1. 利用者がSMS認証する。
2. 事業所名等を入力し、現場合意書の全文を確認する。
3. ご本人のスタッフ同意書も確認し、両方への同意を送信する。
4. Drive上の事業所フォルダと2通のPDF原本を作る。
5. 両方の原本を検証した後、事業所、最初の現場監督者、2件の同意記録をDBで一緒に確定する。

### スタッフ同意

1. 管理者が氏名を入力して仮のスタッフを追加する。
2. サーバーが一回限りで有効期限のある招待リンクを発行する。DBには招待トークンのSHA-256だけを保存する。
3. 管理者がリンクをLINE等で本人へ送る。
4. 本人がリンクを開き、SMS認証して同意書を確認する。
5. スタッフ同意PDFを生成してDriveへ保存する。
6. 原本を検証した後、本人の`identity_id`と`person_id`の所属、同意記録、招待の使用済み状態をDBで一緒に確定する。

スタッフは自分の同意だけを確認でき、事業所のスタッフ一覧は閲覧できない。同じSMS利用者は複数の事業所に所属できる。

## 提供前承認

PCアプリで撮影者や映り込んだスタッフを撮影単位ごとに選ばせない。承認時点で、同じ`site_id`にある保存完了済みの現場合意一件とスタッフ同意一式を並べ、`consent_snapshot`として固定する。

現場監督者または管理者はDesktopで内容を確認し、提供してよい撮影単位だけを承認する。承認対象は、その時点でPC上にある任意形式のファイル一式である。MCAP一つでも、MP4・JSONL等の複数ファイルでも同じ`unit.files`として扱う。承認記録には、承認者、時刻、`unit_id`、全ファイルの相対パス・サイズ・SHA-256、それらから算出した`files_sha256`、同意スナップショット、表示した承認文を含める。

承認後にファイルの追加、削除、変更があった場合は`files_sha256`が一致しなくなるため、アップロードを完了させない。匿名化、アノテーション、販売は別の工程であり、この証跡には含めない。

## 納品時の証跡

`rootlens-evidence.json`には次を記録する。

- `evidence_id`と発行日時
- `site_id`、`unit_id`、承認対象ファイル一式と`files_sha256`
- 承認時点で使用した現場合意とスタッフ同意の`agreement_record_id`
- 各同意PDFの証跡内相対パスとSHA-256
- SMS認証を経た現場監督者の承認記録

証跡一式には、JSONが指す同意PDFのコピーを`agreements/`以下へ同梱する。URL、DriveファイルID、匿名化処理完了日時、提供日時、加工後データは含めない。このファイル単独でRootLens発行者の真正性を証明するものではないが、同梱された撮影データとPDFの変更は各SHA-256との不一致として検出できる。RootLens側ではJSON全体のSHA-256をDBへ保存する。

## 権限

| 操作 | スタッフ | 管理者 | 現場監督者 |
| --- | ---: | ---: | ---: |
| 自分の同意を確認・撤回 | 可 | 可 | 可 |
| スタッフ一覧の閲覧 | 不可 | 可 | 可 |
| スタッフの追加・招待 | 不可 | 可 | 可 |
| スタッフと管理者の権限変更 | 不可 | 可 | 可 |
| 撮影データの承認・アップロード | 不可 | 可 | 可 |
| 現場監督者の付与・解除 | 不可 | 不可 | 可 |
| 事業所の終了 | 不可 | 不可 | 可 |

最後の現場監督者は、自分を解除できない。事業所の終了は証跡とDrive原本を削除せず、今後の操作を止める処理とする。

## 実装順

1. 外部署名サービスと証跡署名処理を削除し、PDF原本生成、Drive保存、DBハッシュ照合へ置き換える。
2. SMS OTPの開始、検証、Webセッションを実装する。
3. 事業所登録と現場合意を一つのフローにする。
4. スタッフの仮登録、招待、SMS認証、個人同意を実装する。
5. DesktopのGoogleログインと事業所認証ファイルを、SMSログイン後のRootLensセッションへ置き換える。
6. 承認時の同意スナップショット、任意形式のファイル一式、同意PDFを一つの証跡JSONへ接続する。
