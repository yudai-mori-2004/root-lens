# 24. Consent evidence chain

## 目的

撮影前の現場合意とスタッフ個人の同意、撮影後の現場監督者による承認、実際に承認された撮影データを、一つの来歴として追跡できるようにする。署名済みPDFの原本はGoogle共有ドライブ「RootLens Submit」に保存し、WebのDBは原本の所在とSHA-256を記録する。

販売先へ渡す`rootlens-evidence.json`は、使用した同意記録、撮影データの承認、raw、納品ファイルを結ぶ索引である。RootLensの署名鍵や第三者証明書は使わない。原本の確認はDrive上のPDFとRootLensのDBに保存したハッシュを照合して行う。

## 当事者が行うこと

### 事業所の登録者

SMS認証でログインし、事業所情報を入力して現場合意書へ同意する。同意が完了すると事業所が作成され、登録者は最初の現場監督者になる。RootLensによる事前審査や利用開始状態の切替は設けない。

### スタッフ

管理者からLINE等で受け取った個別の招待リンクを開き、SMS認証後に撮影参加に関する同意書へ同意する。手書きの署名画像や専用アプリは必要としない。

### 管理者・現場監督者

スタッフの追加と招待、撮影データの確認、承認、アップロードを行う。DesktopはブラウザでのSMSログインからRootLensセッションを取得し、その人が操作できる事業所をAPIから取得する。事業所認証ファイルは使わない。

## 識別子

| 識別子 | 意味 |
| --- | --- |
| `site_id` | 撮影場所・事業所 |
| `person_id` | 一つの事業所に所属する人 |
| `identity_id` | SMS認証済みの利用者 |
| `agreement_record_id` | 一回の現場合意またはスタッフ同意 |
| `unit_id` | 一つの撮影単位 |
| `approval_event_id` | 一つの撮影単位に対する提供前承認 |
| `evidence_id` | 納品時の証跡索引 |

同姓同名は`person_id`で区別する。電話番号そのものは納品物へ含めず、署名PDFには末尾4桁だけを表示する。

## 同意原本

### 原本の構成

同意ごとに新しい`agreement_record_id`とPDFを作る。既存のPDFは上書きしない。PDFには、同意時点の全文と次の電子署名記録を収める。

- 署名者の氏名
- 事業所名
- SMS認証を使用したこと
- 認証した電話番号の末尾4桁
- サーバーが確定した同意日時
- 画面に表示した同意文言
- 文書版
- `agreement_record_id`

署名操作の証拠は、SMS認証済みの`identity_id`、同意操作、確定本文、サーバー時刻を結び付けたDB記録である。手書き風の画像は付けない。

### DriveとDBの役割

```text
RootLens Submit/
  現場データ収集/
    <事業所名>/
      現場合意書/
        site-agreement__<agreement_record_id>.pdf
      スタッフ同意書/
        staff-consent__<agreement_record_id>.pdf
      承認済みデータ/
        <unit_id>/
          approval-receipt.json
          ...撮影データ
```

Driveファイルには`agreement_record_id`、`site_id`、文書種別、文書版を`appProperties`として付ける。DBには次を保存する。

- `agreement_record_id`
- `site_id`と、スタッフ同意の場合は`person_id`
- SMS認証済みの`identity_id`
- PDFへ表示した署名者名と電話番号の末尾4桁
- 文書版とテンプレートのSHA-256
- 同意文言と同意日時
- DriveファイルID
- 保存後にDriveから確認したPDFのSHA-256
- Driveへの保存完了日時

Driveの版履歴には依存しない。改定または再同意では新しいPDFを作り、以前のPDFを残す。撤回も原本を変更せず、別のイベントとして記録する。

### Driveとの同期

署名開始時に`agreement_record_id`とDriveファイルIDを一度だけ割り当てる。同じ署名要求を再送した場合は同じIDを使い、既に同じPDFが保存されていれば新しいファイルを作らない。

保存処理は次の順で行う。

1. SMS認証済みの利用者と対象文書を確定する。
2. DBに署名日時、同意文言、文書版、割り当てたDriveファイルIDを記録する。
3. 同じDB記録からPDFを生成する。
4. PDFを新規ファイルとしてDriveへ保存する。
5. Driveからファイルを再取得し、サイズ、保存先、`appProperties`、SHA-256を確認する。
6. DBへPDFのSHA-256と保存完了日時を記録する。

通信が途中で失敗した場合は、同じ記録から2以降を再開する。保存完了日時がない同意記録は、撮影データ承認時の同意一覧へ含めない。これは利用可否を人が切り替える状態ではなく、Drive保存の完了を示す同期記録である。

## 事業所とスタッフの通常フロー

### 事業所登録

1. 利用者がSMS認証する。
2. 事業所名等を入力し、現場合意書の全文を確認する。
3. 「上記内容を確認し、合意します」を押す。
4. 事業所、最初の現場監督者、Drive上の事業所フォルダを作る。
5. 現場合意書PDFを生成し、現場合意書フォルダへ保存する。
6. 保存後のPDFハッシュをDBへ記録する。

### スタッフ同意

1. 管理者が氏名を入力して仮のスタッフを追加する。
2. サーバーが一回限りで有効期限のある招待リンクを発行する。DBには招待トークンのSHA-256だけを保存する。
3. 管理者がリンクをLINE等で本人へ送る。
4. 本人がリンクを開き、SMS認証して同意書を確認する。
5. 本人の`identity_id`を仮登録された`person_id`へ結び付ける。
6. スタッフ同意PDFを生成してDriveへ保存し、DBへPDFハッシュを記録する。

スタッフは自分の同意だけを確認でき、事業所のスタッフ一覧は閲覧できない。同じSMS利用者は複数の事業所に所属できる。

## 提供前承認

PCアプリでクリップごとの撮影者や映り込んだスタッフを選ばせない。承認時点で、同じ`site_id`にある保存完了済みの現場合意一件とスタッフ同意一式を並べ、`consent_snapshot`として固定する。

現場監督者または管理者はDesktopで映像と音声を確認し、提供してよい撮影単位だけを承認する。承認記録には、承認者、時刻、`unit_id`、rawファイル一覧とSHA-256、同意スナップショット、表示した承認文を含める。

承認後にrawが変わった場合は、保存されたファイルハッシュと一致しなくなるためアップロードを完了させない。

## 納品時の証跡

`rootlens-evidence.json`には次を記録する。

- 元となる`unit_id`とrawファイルのSHA-256
- 承認時点で使用した現場合意とスタッフ同意の`agreement_record_id`
- 各同意PDFのSHA-256
- 現場監督者の承認記録
- 加工後の納品ファイル一覧とSHA-256
- 匿名化処理完了日時と提供日時
- RootLens上の照合ページ

このファイル単独でRootLens発行者の真正性を証明するものではない。販売先は照合ページを通じて、RootLensのDBに保存された記録と一致することを確認する。納品後のファイル変更は、各ファイルのSHA-256との不一致として検出する。

## 権限

| 操作 | スタッフ | 管理者 | 現場監督者 |
| --- | ---: | ---: | ---: |
| 自分の同意を確認・撤回 | 可 | 可 | 可 |
| スタッフ一覧の閲覧 | 不可 | 可 | 可 |
| スタッフの追加・招待 | 不可 | 可 | 可 |
| スタッフと管理者の権限変更 | 不可 | 可 | 可 |
| 撮影データの承認・アップロード | 不可 | 可 | 可 |
| 現場監督者の付与・解除 | 不可 | 不可 | 可 |
| 事業所の終了 | 不可 | 不可 | 可 |

最後の現場監督者は、自分を解除できない。事業所の終了は証跡とDrive原本を削除せず、今後の操作を止める処理とする。

## 実装順

1. 外部署名サービスと証跡署名処理を削除し、PDF原本生成、Drive保存、DBハッシュ照合へ置き換える。
2. SMS OTPの開始、検証、Webセッションを実装する。
3. 事業所登録と現場合意を一つのフローにする。
4. スタッフの仮登録、招待、SMS認証、個人同意を実装する。
5. DesktopのGoogleログインと事業所認証ファイルを、SMSログイン後のRootLensセッションへ置き換える。
6. 承認時の同意スナップショットと納品時の照合ページを新しい同意原本へ接続する。
